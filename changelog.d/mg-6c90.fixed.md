- **Two load-sensitive test assertions are now RELATIVE, so a busy host no
  longer fails innocent branches at the merge gate (mg-6c90).**
  `TestGateWatchMeasuresARealSubtreesCPU` required a gate holding one spinner to
  peak above **0.5 cores**, and `TestStatusAssignee_LiveAppliesPerRefresh`
  required **2 live frames inside a 400ms window**. Both are demands for a
  minimum share of a SHARED resource inside a fixed window, and a loaded host
  will not grant one.

  **The assertion was wrong in kind, not in magnitude.** Byte-identical binaries
  built from `main` and from the branch under review measured 4/4 PASS at load
  4.6-5.3 and 13/13 FAIL at load 52-106; the frame-count assertion failed 3/3 on
  a branch and 3/3 on a clean `origin/main` worktree, same box, same minute. And
  the CPU test was separately observed to PASS at load 154 *in isolation*, which
  disqualifies "the box is busy" as the explanation and names the real one:
  **contention inside the measurement window.** `0.5 cores` was never a property
  of gatewatch — it was a property of what the scheduler granted during those
  seconds. So no replacement threshold would have been correct, and widening it
  would only have bought silence.

  Between them the two cost five innocent branches in one evening, each a gate
  run of 6-26 minutes plus an individual exoneration so the branch owner did not
  go hunting a defect in their own diff, and two resubmissions because the owner
  had been reaped in the meantime. The worse cost was habituation: by the fourth
  occurrence the coordinator was reading `FAIL internal/refinery` as noise before
  checking, which is the state in which a real refinery regression merges
  unnoticed. That is why this was fixed rather than tolerated.

  **What the CPU test now proves.** Three arms instead of two — a sleeping gate,
  a gate holding one spinner, and a gate holding four, all built from one
  template so parallelism is the only thing that differs — and every rule is a
  comparison between them. The load-bearing one is new: the four-spinner arm
  must measure at least **1.5x** the one-spinner arm, where fair share predicts
  4x. That is what proves the number is a *function of the injected work* rather
  than merely non-zero, so a constant-returning instrument, one that measures
  the whole host, and one that loses the descendants all fail it — and it is
  load-independent by construction, because schedulers allocate per runnable
  thread and contention scales both arms together. The upper bounds are kept as
  absolutes, deliberately: contention can only push a measurement down, so a
  ceiling is never made unmeetable by a busy host, and the ceiling is what
  catches a CPU column too coarse for the window quantising work into bursts.

  **Measured across the range, which is the claim that matters.** Over eight
  runs on this 10-core host spanning load 17 to load 248, the one-spinner arm —
  the quantity the old floor keyed on — fell from **0.33 cores to 0.06**, a
  factor of five, and never once reached the retired 0.5 threshold outside a
  quiet box. The ratio over the same span ran **2.90x to 3.86x**. The quantity
  moved by 5x; the verdict did not move at all.

  The ratio compares the arms' MEANS rather than their peaks, and that is not
  cosmetic. A peak is a biased estimator and the two arms are not biased
  equally: the one-spinner arm is noisy so its highest of ~8 readings sits well
  above its centre, while the four-spinner arm has already averaged four
  spinners. Comparing peaks therefore compresses the ratio, and compresses it
  *more the busier the box is* — 3.3-4.0x at load 42-49 but 1.8-2.5x at load
  174-210. A margin that erodes with load is the same defect in a subtler form,
  so the estimator was corrected rather than the threshold lowered to
  accommodate it.

  **The one floor that remains is the production classifier's own.** The
  one-spinner arm must still classify as `SubtreeBusy`, which needs 0.02 cores —
  `subtreeIdleCores`, not a number invented for the test. An instrument that
  calls a real spinner idle is reporting a real defect at any load. Its margin is
  stated rather than assumed: a single spinner receives about `10/(load+1)` cores
  here, so 0.19 at load 52 and 0.055 at load 180 — the worst this box has
  recorded in a night — against a 0.02 floor, going under only past load ~500.

  **The frame-count test now WAITS for the second frame** instead of budgeting
  400ms for it, to a 60s deadline. On a quiet box the frame lands in ~170ms and
  nothing changes; on a loaded one the test takes longer instead of going red.
  Measured over five consecutive runs at load 40, the wait was 516ms, 169, 176,
  189, 173 — the first of those would have failed the old 400ms budget, on the
  same box within the same minute as the other four.

  **Both changes are demonstrated able to fail**, because the whole problem was
  that everyone had learnt to read red as load.
  `TestGateWatchRulesGoRedWhenTheWalkMissesTheSubtree` runs a real gate with a
  real spinner and only the subtree walk blinded — every process rewritten to
  look like an orphaned group leader, which is exactly the instrument pogo had
  before mg-0c51 — and asserts the rules complain; they do, three times, naming
  the walk. `TestSubtreeCPURulesSurviveContentionAndCatchABlindInstrument` runs
  the rules against five broken instruments and against correct ones on hosts
  granting 1.0 down to 0.025 cores, asserting the verdict is unchanged across
  that 40x range. The frame-count deadline was verified red by hand against a
  live loop that renders once and stops.

  **The rule is written down** in `docs/development.md` ("Tests that measure a
  shared resource"), because the ticket's own warning was that this gets
  rediscovered one test at a time. A sweep of the suite for the class — minimum
  CPU share, minimum frame or sample count in a fixed window — found these two
  and no third; the CPU and sample-count assertions in `internal/wedgewatch`,
  `internal/hostload`, and the rest of `internal/refinery` are made against
  injected samples and so cannot be moved by host load, and the ~20 remaining
  `elapsed > N` bounds are the safe direction.

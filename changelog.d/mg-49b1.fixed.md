- **Boot-time schedule re-registration became a check, and the reason that kept
  regenerating it was deleted rather than reworded (mg-49b1).** Nine shipped
  prompts — `mayor.md`, `crew/doctor.md`, `pm/pm-template.md` and all six
  `templates/polecat*.md` — told their agent to re-register its `pogo schedule`
  ids unconditionally on startup, justified as "idempotent via `--id`, so
  re-running it costs nothing". They now check first (`pogo schedule list
  --agent <you>`) and register only an id that is missing or whose cron is wrong.

  The justification is the part that had to go. `--id` **is** the dedup key, so
  the first half is true and you will not stack duplicates — but "does not
  duplicate" was being read as "costs nothing", and it is not: re-registering
  REPLACES the entry and zeroes its lifetime completion counters. Measured
  against the running daemon on 2026-08-12 — `mail-check-mg-49b1` read `1/1`
  before and `—` after, with one `pogo schedule` call in between. Those counters
  are how `internal/ackwatch` tells a fire that was *worked* from one that merely
  arrived, which is the discrimination the 23h30m outage of 2026-07-22 was
  invisible for the want of; doing this at boot discarded it on every boot,
  including the boot after an outage.

  **Two premises the ticket rested on turned out to be already fixed, and the
  prompts now say so explicitly so they are not re-derived.** The originating
  report was that re-registration *discards an outstanding fire* — the catch-up
  fire the agent booted to handle. That was true, and it was fixed the evening
  before the report by mg-3cbb (`carryOutstandingFireLocked`), which carries a
  still-redeemable token across a same-`(agent, id)` re-register; verified live,
  the fix is an ancestor of the running daemon's revision. The proposed remedy of
  "ack before you re-register" is therefore **not** in this change: it would have
  encoded a dead bug and left the destructive step in the procedure. The reporter
  retracted the premise independently, noting that the `—` presented as the
  symptom was `TestReregistration_StillZeroesTheLifetimeCounters` working.

  The second premise was mg-de08, whose ruling made unconditional re-registration
  load-bearing because a pogod bounce reaped the fleet's `mail-check-*`. That was
  mg-de08's own option (2) — the one the ticket called "cheap, partial" and
  described as leaving the fleet's mail loop resting on prompt wording. Option
  (1) shipped instead about two hours later (`cmd/pogod/gcgate.go`, 7a2dc7f,
  "never reap a mail-check without positive evidence of death"): an absent
  registry entry is now UNKNOWN rather than GONE, and the reap is held until the
  first auto-start sweep plus a settle window. Also verified live. The prompt was
  carrying a workaround for a bug fixed in code a month ago.

  **What mg-de08 does leave behind shaped the replacement.** Its proximate cause
  was a check-then-skip that *failed*: a PM ran `pogo schedule list`, saw its two
  sweeps still present (they are not named `mail-check-*`, so they survived the
  reap), concluded "already registered", and never noticed the reaped id was the
  third one — then looked scheduled, answered nudges and diagnosed healthy with
  no mail loop for two hours. A check-then-repair procedure is an artifact of
  exactly the kind that failed there, so every rewritten prompt states that the
  check is against a **specific id**, not against the listing being non-empty,
  and cites mg-de08 at that point so the reason travels with the rule.

  `internal/agent/schedulecheckfirst_test.go` pins the shape rather than the
  sentence: any shipped prompt containing a `pogo schedule <agent> --cron`
  registration must also contain the `pogo schedule list` check, must place that
  check **before** the registration (an agent reading top-down meets the check
  first), must carry a directive leaving a correct id alone, and must state the
  per-id rule. Four positive controls regress real corpus text the way a tidying
  pass would and assert each is flagged, so a green run means something.

  Two prompts also gained a boot-time **mail** reconcile, which has the same
  shape: a mail that lands between an agent's last heartbeat and a bounce is
  read-but-unhandled and invisible to the unread filter forever after, so
  `mayor.md` and `pm-template.md` now say to reconcile with `mg mail list <you>
  --all` against the last heartbeat rather than trusting the default filter.

  **This does not reach the running coordinator.** `~/.pogo/agents/mayor.md`
  carries local edits, so pogod declines the shipped update and diverts it to
  `mayor.md.dist` (mg-5b9a, currently parked). This lands the fix for every other
  deployment and every future install; the live mayor keeps the old text until
  mg-5b9a is reconciled.
